Project 02 · Streaming data platform

Real-Time Streaming & Medallion Lakehouse

A 100% local lakehouse that ingests live e-commerce order events from Redpanda, cleanses and deduplicates them with event-time watermarks in PySpark Structured Streaming, and lands Bronze → Silver → Gold Delta Lake tables — checkpointed, compacted with OPTIMIZE/Z-ORDER, and served to stakeholders through a live dashboard. 01 The problem

One broker, one consumer, one truth

A stream of order events arrives in a Kafka topic. Everything downstream has to be replayable, deduplicated and auditable — without a second consumer and without silently losing late data.

Replayable

Bronze is an immutable Delta log. Silver reads the Bronze stream, so the pipeline can be rebuilt from the log without touching Kafka twice.

Deduplicated

Events arrive twice, and late. The dedup key event_id + event_time with a 20-minute watermark keeps every valid order and drops every repeat.

Auditable

Bronze → Silver → Gold, each with its own grain, its own verification script and its own row count you can check by hand.

02 Architecture

Four hops, one broker, zero magic

Producer → Redpanda → Bronze → Silver → Gold → dashboard. The broker is touched by exactly one job; everything after Bronze is a Delta table on disk.

The data path

Producer ──produce──▶ Redpanda
──readStream──▶ BRONZE (delta)
──readStream(delta)──▶ SILVER (dedup)
──batch + live refresh──▶ GOLD (aggregate)
──every 10 s──▶ metrics.json ──▶ dashboard :8501

Why the watermark is 20 minutes

The producer delays 10% of events by 2–15 minutes. With a 10-minute watermark Spark silently dropped 137 valid orders in append-mode dedup. Sizing the watermark above the maximum lateness (20 min) fixed it: numRowsDroppedByWatermark = 0 and Silver keeps all 3,018 distinct keys.

Why Silver reads Bronze, not Kafka

One consumer, one source of truth. A replay re-reads the Delta log instead of re-consuming the topic, and the offsets of the Bronze job are the only Kafka offsets in the system.

Why Gold is overwritten, not merged

Gold is a derived aggregate. A full recompute with mode=overwrite is idempotent, needs no merge bookkeeping, and automatically corrects late events that land after a previous cycle.

04 Engineering concerns

The five things that actually bite

Late data

Event time ≠ processing time. The watermark must sit above the maximum lateness, otherwise dropDuplicates in append mode discards rows it has never seen. Measured and fixed: 20 min, zero dropped rows.

Idle detection

numInputRows is per micro-batch, so a naive supervisor sees a constant number and declares "idle" mid-stream. Counting rows monotonically per (query, batchId) fixed an early stop at 2,574 of 3,277 rows.

Small files

Five-second micro-batches write a file each. OPTIMIZE with ZORDER BY (seller_id) took active files from Bronze 3→1, Silver 4→1, Gold 1→1 and made the Gold table readable in one scan.

Fault tolerance

After a docker kill mid-stream, the checkpoint resumed from the committed offsets: Silver 4,315 = 4,315 distinct keys, offsets contiguous per partition (1682 / 1809 / 1424).

Quarantine

Unparseable rows go to a sibling Delta table, not inside Silver — a nested path would silently become part of the Silver table and corrupt its counts.

Serving safely

The dashboard never touches Delta. A refresher writes one atomic JSON snapshot and a read-only stdlib server serves it — no Spark in the web tier, no credentials in the browser, no possibility of the UI mutating the lakehouse.

06 Live dashboard

The dashboard lives on its own page

A read-only stakeholder view of the Gold layer: revenue, orders, average order value, top sellers, payment mix, hourly revenue, duplicates removed, lateness and pipeline health. It polls /api/metrics every 3 seconds and never falls back to sample data — if the pipeline is not running it says so.

Open it

The dashboard is a separate page of this site, and the same page is what the local container serves on http://localhost:8501.

Open dashboard.html →

bash scripts/live_dashboard.sh

How it is wired

spark/gold_refresh.py recomputes Gold from Silver every 10 s and writes an atomic metrics.json. dashboard/server.py serves it with the Python standard library only — no Spark in the web tier, no third-party packages, no CDN.

spark/gold_logic.py is shared with the batch compaction job, so the live view can never drift from the batch Gold table.

07 Trade-offs

Streaming is a batch problem wearing a hat

Structured Streaming is an incremental batch loop. It buys sub-minute latency and pays for it with always-on compute, stateful complexity and small files.

Continuous streaming vs. scheduled batch
DimensionContinuous streaming · this projectMicro-batch every 15 min
Latencysecondsminutes
Costalways-on driver + executorscompute only during the run
Complexitywatermarks, state, checkpointsplain batch
Small filesmany → needs OPTIMIZEone set per run
Choose whensub-minute freshness SLOminutes of latency are acceptable

08 How to run

Four commands, no cloud account

terminaldocker compose · local
# 1 · build + start Redpanda, Console, topic
docker-compose build spark && docker-compose up -d

# 2 · emit events (60s @ 50/s, reproducible seed)
docker-compose run --rm producer python event_producer.py --duration 60 --rate 50 --seed 42

# 3 · Kafka → Bronze → Silver
docker-compose run --rm spark spark-submit \
  --packages org.apache.spark:spark-sql-kafka-0-10_2.12:3.5.3,io.delta:delta-spark_2.12:3.2.0 \
  /opt/spark/app/stream_ingestion.py

# 4 · Gold aggregate + OPTIMIZE / ZORDER
docker-compose run --rm spark spark-submit --packages io.delta:delta-spark_2.12:3.2.0 \
  /opt/spark/app/gold_compaction.py

# 5 · optional · live dashboard (refresher + UI + producer)
bash scripts/live_dashboard.sh   # open :8501

Redpanda Console → localhost:8080 · Spark UI → localhost:4040 · Dashboard → localhost:8501 · Full steps in RUNBOOK.md.
