Real-Time Streaming & Medallion Lakehouse Pipeline

A 100% local lakehouse that ingests live e-commerce order events from Redpanda, cleanses and deduplicates them with event-time watermarks in PySpark Structured Streaming, and lands Bronze → Silver → Gold Delta Lake tables — with checkpointed fault tolerance and OPTIMIZE/Z-ORDER compaction. Every number below was measured.

View on GitHub See measured results Concepts & decisions README

01The problem

Raw, event-driven commerce data is messy and out of order: the same event gets retried, events arrive minutes late, and downstream analytics must be correct anyway.

We need a pipeline that (1) never loses a record, (2) removes duplicates without unbounded state, (3) copes with late events, (4) survives crashes without double-writing, and (5) keeps the tables fast as they grow. This project implements exactly that shape — and proves each guarantee with a test and a measured number.

02Architecture

Only the Bronze query consumes Kafka; Silver replays Bronze as a Delta stream, so the broker has a single consumer and Silver can be rebuilt from Bronze.

04Key engineering concerns

Stateful dedup

dropDuplicates(["event_id","event_time"]) after a 10-minute watermark. event_id is identity; event_time lets the watermark expire state, so it never grows unbounded.

Late data

The producer delays events 2-15 min while the watermark tolerates 10 — so late duplicates beyond tolerance can slip through. A deliberate, documented completeness-vs-state trade-off.

Checkpointing

One checkpoint per query (bronze, silver, quarantine). Delta + checkpoint = idempotent, effectively-once writes; a replayed micro-batch never double-lands.

Fault tolerance

An ungraceful docker kill mid-batch, then restart: Silver stays duplicate-free and Bronze offsets stay contiguous per partition.

Compaction

5-second micro-batches create small files. OPTIMIZE compacts Bronze/Silver; Gold gets ZORDER BY (seller_id) for the top filter.

Single Kafka consumer

Only Bronze reads Kafka; Silver reads the Bronze Delta stream. One owner of offsets, and Silver is rebuildable by replaying Bronze.

06Trade-offs: streaming vs. scheduled batch

Structured Streaming is an incremental batch loop. It buys low latency at the cost of always-on compute and stateful complexity.

DimensionContinuous streaming (this project)Micro-batch every 15 min
Latencysecondsminutes
Costalways-on driver + executorscompute only during the run
Complexitywatermarks, state, checkpointsplain batch
Small filesmany → needs OPTIMIZEone set per run
Choose whensub-minute freshness SLOminutes of latency acceptable

07How to run

# start the stack (Redpanda, Console, topic-init, Spark)
docker-compose build spark && docker-compose up -d

# emit events (60s @ 50/s, reproducible)
docker-compose run --rm producer python event_producer.py --duration 60 --rate 50 --seed 42

# Kafka -> Bronze -> Silver
docker-compose run --rm spark spark-submit \
  --packages org.apache.spark:spark-sql-kafka-0-10_2.12:3.5.3,io.delta:delta-spark_2.12:3.2.0 \
  /opt/spark/app/stream_ingestion.py

# Gold aggregate + OPTIMIZE / ZORDER
docker-compose run --rm spark spark-submit --packages io.delta:delta-spark_2.12:3.2.0 \
  /opt/spark/app/gold_compaction.py

# verify + recovery
docker-compose run --rm spark spark-submit --packages io.delta:delta-spark_2.12:3.2.0 /opt/spark/tests/verify_silver_dedup.py
bash tests/verify_recovery.sh

Console · localhost:8080  ·  Spark UI · localhost:4040. Full steps in docs/RUNBOOK.md.
